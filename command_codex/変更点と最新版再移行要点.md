# aidiy_codex の変更点と最新版再移行要点

`command_codex/codex-rs/` は OpenAI Codex（[openai/codex](https://github.com/openai/codex) の `codex-rs/`）を AiDiy に内包したものです。
本書は、AiDiy が upstream に加えた変更の一覧と、upstream の最新版へ移し替えるときの要点をまとめます。
方針・構成は [AGENTS.md](AGENTS.md)、コンパイル手順は [`_compile.py`](_compile.py) 冒頭を参照してください。

## ライセンス上の位置づけ

- 同梱 Codex は **Apache License 2.0**（[codex-rs/LICENSE](codex-rs/LICENSE)、Copyright OpenAI）です。GPL ではありません。[codex-rs/NOTICE](codex-rs/NOTICE)（Ratatui 由来部分の MIT 表示を含む）とともに `codex-rs/` 内に維持します。
- Apache-2.0 第4条に従い、配布物には LICENSE と NOTICE を同梱し、変更したファイルには変更した旨を示します。AiDiy では変更・追加した箇所に `AiDiy:` のコメントを付け、本書を変更点の一覧とします。
- AiDiy 独自部分（`_compile.py`、`aidiy/`、本書）は [リポジトリルートの LICENSE](../LICENSE) に従います。同梱 Codex のライセンス表示と混同して一括置換しません。
- `aidiy_codex` の名称・アイコンは OpenAI による承認・提携を示すものではありません（[LICENSE_ICONS.md](../frontend_diag/static/LICENSE_ICONS.md)）。

## 取り込み元

- upstream main の `codex-rs/` のみ（ワークスペース版 `0.0.0`）。npm パッケージ、SDK、ドキュメント、CI 設定、upstream ルートのファイルは同梱しません（`.cargo/config.toml` だけを `codex-rs/.cargo/` へ移設）。
- 取り込んだ upstream のコミットは、現時点では記録していません。次回の再移行では、取り込んだコミット ID と日付を下の「再移行の記録」に残してください。

### 変更による動作の違い（upstream との差）

- **マルチプロバイダ:** `--model <区分>/<モデル名>`（openai_oauth / openai_chat / xai_oauth / claude_chat / gemini_chat / freeai_chat / openrt_chat / openrt_free / ollama_chat / local_chat）で、Hermes / Pi と同じ接続先へつなぐ。`--provider` などの指定や `model_provider` の選択肢は増やさない。区分ごとの接続方式は [AGENTS.md の「区分ごとの接続」](AGENTS.md#区分ごとの接続)。
- **接続方式:** Responses に加え Chat Completions と Anthropic Messages。core の再試行・認証・ツール実行・サンドボックスは upstream のまま。
- **認証:** openai_oauth は upstream の ChatGPT ログイン（`~/.codex`）のまま。他の区分は upstream の設定項目（`experimental_bearer_token`、`http_headers`、`auth` コマンド）へ AiDiy のキーを入れるだけで、upstream の認証処理は変えない。xai_oauth だけ内部名のトークン取得を Rust で行う。
- **送る版番号:** 設定 JSON の `client_version`（既定 `0.169.0`）。サーバーは版でモデルを出し分けるため、`0.0.0` のままでは新しいモデルを使えない。
- **変えていないもの:** TUI、ツール、サンドボックス、app-server、`/model` の挙動。

## 最新版への再移行手順

1. **取得:** upstream の最新版を別フォルダへ取得し、`codex-rs/` だけを使う。取り込むコミット ID と日付を控える。
2. **退避:** 現在の `command_codex/codex-rs/` を別名で残す（差分の確認と、追加ファイルの取り出しに使う）。`~/.aidiy/cache/codex/target` は版が変わると再利用できないため、空き容量が足りなければ全体 cleanup で削除する。
3. **差し替え:** `command_codex/codex-rs/` を新しい `codex-rs/` に置き換える。`LICENSE` / `NOTICE` は新しい版のものを使う（AiDiy 側で書き換えない）。
4. **移設:** upstream ルートの `.cargo/config.toml` を `codex-rs/.cargo/config.toml` へ移し、出典コメント（`AiDiy: moved from ...`）を付ける。
5. **追加ファイルを戻す:** 上の「追加したファイル」5つ（テストを含む）を退避した旧版からコピーする。
6. **変更を再適用:** 旧版で `rg -n "AiDiy" codex-rs` に出る箇所を、上の「変更したファイル」の表に沿って新版へ当て直す。upstream 側の構造が変わっていれば、下の「上流の変化に注意する箇所」を見て合わせ直す。
7. **版と依存:** `Cargo.toml` の `[workspace.package] version` を `0.169.0` にし、`model-provider-info/Cargo.toml` に `serde_json` を加えてから `cargo update --workspace --offline` で `Cargo.lock` を合わせる（それ以外の依存は更新しない）。`rust-toolchain.toml` の版が上がった場合は、llvm-mingw で gnullvm ターゲットがビルドできるかを最初に確認する。
8. **確認:** 下の「確認方法」を上から順に行い、終わったら「再移行の記録」に追記する。

## 上流の変化に注意する箇所

再移行で壊れやすい、upstream の構造に依存している箇所です。

- **`WireApi`（model-provider-info）:** 値の追加・Deserialize の書き方・削除済みエラー定数が変わっていないか。`remote.rs` の proto 対応付けも合わせる。
- **`core/src/client.rs`:** `stream()` の HTTP / WebSocket の振り分けと、HTTP 実行部（`ResponsesHttpExecutor`）の構造。`ResponsesApiRequest` を作る箇所（`model:` を `aidiy_api_model()` にする2か所）。
- **Responses 要求の JSON 形:** Chat / Anthropic の変換は、`ResponsesApiRequest` をシリアライズした JSON の `input` / `tools` と、項目の `type`（`message` / `function_call` / `function_call_output` / `custom_tool_call` / `custom_tool_call_output`、ツールの `function` / `custom` / `namespace`）に依存する。名前や形が変われば変換を直す。
- **`ResponseEvent` / `ResponseItem`:** `Created`、`OutputItemAdded`、`OutputTextDelta`、`OutputItemDone`、`Completed`（`TokenUsage`）と、`FunctionCall`（namespace を含む）・`CustomToolCall` の形。
- **`core/src/config/mod.rs`:** プロバイダ ID の決定順（`required_model_provider`、`model_provider`、`cfg.model_provider`）と `model_providers` の組み立て。
- **モデル情報の検索:** models-manager の `find_model_by_namespaced_suffix()`（`openai_oauth/gpt-…` からモデル情報を引く）が残っているか。無くなった場合は区分を外して検索する処理が要る。
- **app-server の既定モデル置き換え:** `allow_provider_model_fallback` が exec で既定（無効）のままか。有効になると区分付きの名前が既定モデルへ置き換わる。
- **認証:** `external_bearer.rs` の `run_provider_auth_command()`、`login` の `OAuthClient` / `TokenEndpoint` / `create_client()`（`aidiy_grok.rs` が使う）、`ModelProviderAuthInfo` の項目。
- **版番号:** `default_client.rs` の User-Agent と `models-manager` の `client_version_to_whole()`。サーバーが求める最低版が上がった場合は、再ビルドせず設定 JSON の `client_version` を上げて確認できる。
- **モデル一覧の取得条件:** `models_endpoint.rs` の `has_command_auth()` と、models-manager の `should_refresh_models()`。

## 確認方法

1. 変更箇所の確認: `rg -n "AiDiy" command_codex/codex-rs --glob '!target'` で、上の表の全ファイルが出ること。
2. 単体テスト（`_compile.py` と同じ環境で。デバッグ成果物が十数 GB 増えるので、終わったら `~/.aidiy/cache/codex/target/<target>/debug` を消す）:
   - `cargo test -p codex-model-provider-info aidiy` と `cargo test -p codex-model-provider-info chat_wire_api`
   - `cargo test -p codex-api chat_completions` と `cargo test -p codex-api anthropic`
   - `cargo test -p codex-login aidiy`
   - `cargo test -p codex-model-provider models_endpoint`
3. AiDiy 側: `python -m unittest scripts/checks/test_setup_codex.py scripts/checks/test_codex_compile_cancel.py`、`node --test frontend_diag/checks/codex-info.check.mjs frontend_diag/checks/models-info.check.mjs`。
4. ビルド: `python command_codex/_compile.py --yes`（release）。`aidiy_codex --version` が `codex-cli 0.169.0` であること。
5. 実接続（有料 API を含むため、利用者の了承を得て区分ごとに 1 回だけ）: `aidiy_codex exec --skip-git-repo-check --sandbox read-only --ephemeral -m <区分>/<モデル名> "Reply with the single word OK."` を各区分で実行し、`OK` が返ること。キー・トークンは表示・記録しない。
