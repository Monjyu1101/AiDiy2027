# aidiy_codex の変更点と最新版再移行要点

`command_codex/codex-rs/` は OpenAI Codex（[openai/codex](https://github.com/openai/codex) の `codex-rs/`）を AiDiy に内包したものです。
本書は、AiDiy が upstream に加えた変更の一覧と、upstream の最新版へ移し替えるときの要点をまとめます。
方針・構成は [AGENTS.md](AGENTS.md)、コンパイル手順は [`_compile.py`](_compile.py) 冒頭を参照してください。

## セットアップのランチャー登録案内

- `_compile.py` のランチャー登録成功時は、本体のコンパイル完了後に利用できることだけを案内する。共通セットアップと合わせて端末の開き直し案内は表示しない。登録処理・PATH登録と失敗時の警告は変更しない。

## CLI chat の JSON 形式修正

- `core/src/aidiy_cli.rs` / `aidiy_cli_json.rs`：子CLIが正常終了した場合だけ回答を解析し、JSON構文不正・JSON欠落に限って同じCLIへ1回形式修正を要求する。履歴・モデル・ツール定義は維持し、失敗した回答はデータとして引用する。生回答をログに出さない。
- 重複キー、JSON配列、ツール名・引数・schema違反、CLI実行・認証失敗は再要求で回避せず拒否する。最初の不正回答からはツールイベントを発行しない。修正も失敗したら停止する。中断は再要求中も子プロセスの回収を適用する。
- 形式説明にはJSON文字列内の引用符・改行・バックスラッシュのエスケープと、引数は文字列でなくobjectで返すことを明記する。反映には再コンパイルが必要。実CLIの認証・モデル個別の回答品質は別途確認する。
## 現行モデルのオフライン既定値

- `models-manager/src/manager.rs`：OpenAI系のオフライン既定候補を `gpt-6.2-sol` / `gpt-6.2-astra` に更新する。新モデルの能力・価格は未確認のため、旧モデルの仕様をコピーせず既存の汎用フォールバックを使用する。汎用コンテキスト上限も新モデルの公式仕様を表す値ではない。サーバー取得メタデータがある場合は従来どおり取得結果を使う。
- 保存済みの旧モデル指定は強制移行しない。`models.json` はBedrock/GCPの旧モデル定義からも参照されるため維持し、サービス固有ID・過去のsnapshot・移行資料も一括置換しない。Diag生成の区分付きカタログがAiDiy選択候補の正本である。
- 例示・AiDiy区分解析と状態バーの回帰入力は現行IDへ更新。反映には再コンパイルが必要。

## 左下モデル表示の統一

- `tui/src/chatwidget/status_surfaces.rs` / `provider_label.rs`：左下の `model` / `model-with-reasoning` は `プロバイダ/モデル` を表示する。カタログの表示別名ではなく選択中のモデルIDを使い、AiDiy区分（OAuth / API / CLI）付きIDへ二重にプロバイダを付けない。区分のないモデルは現在の接続プロバイダIDを補い、OpenRouter等の `vendor/model` はモデル側に維持する。
- 区分の判定は `model-provider-info/src/lib.rs` から公開した既存 `split_aidiy_model` とCLI区分parserを再利用し、UI側へ区分一覧を複製しない。
- 推論レベル・速度表示と既存の幅調整は維持する。端末タイトルと `/status` はこの変更の対象外。モデル切替・復帰、既存prefix、幅30/80のフッター描画を回帰確認する。反映には本体の再コンパイルが必要。

## Windows clone 用 snapshot 名の短縮（70文字目標）

- ファイル名単体を **70文字以内** にするため、Codexのsnapshot名から自動付加される長いモジュール接頭辞を外した。各外部snapshot assertionを `insta::with_settings!({prepend_module_to_snapshot => false}, { ... })` で囲み、既存のsnapshot保存先・OS別suffix・filters等はそのまま継承する。ライブラリinstaのforkは行っていない。`?` / `.await` を含む17個の評価式は元の関数文脈で先に評価し、その値だけを同期Insta設定内へ渡す。
- さらに名前自体が長いものは短い明示aliasまたは短いテスト関数名へ変更した。同じ保存先の `snapshots` という名前9件は、`agents_md_snapshots` 等の役割名を加えて衝突を避ける。ChatWidget用独自macroが手動付加していた接頭辞も外し、ファイル参照を合わせた。テストの評価式・期待値の内容は変更しない。inline snapshotは改名対象外。
- `scripts/checks/codex_snapshot_renames.json` が全1,787件の旧名・新名対応表、`codex_snapshot_aliases.json` が最初の個別短名31件の対応表。upstream更新では、追加・移動・OS別snapshotと同じ保存先の大文字小文字無視の衝突を確認する。`.snap` は期待値として必要なので削除・ignoreしない。
- 全ファイル名70文字以内の回帰チェックは `python -m unittest discover -s scripts/checks -p test_repository_paths.py`。新規snapshotを追加したら短名の規則と対応表へ反映する。長い意味説明はテストコメントに残す。リポジトリ相対パスは180 UTF-16単位以内のチェックも維持する。
- 同じInsta版を使った独立の名前解決検証は [`snapshot_names`](../scripts/checks/snapshot_names/README.md)。これは期待値のlookupと命名ルールの確認であり、Codex本体の描画・会話処理テストの代わりではない。
- 任意の深さのclone先まで保証するものではないため、`_auto.bat` の `core.longpaths=true` も維持する。

## コンパイルの並列数

`_compile.py` は `--jobs` が省略された場合、Cargo に並列数を任せる。メモリ量からの独自の上限計算は行わない。`codex-rs/Cargo.toml` の release の `codegen-units = 4` も外し、コード生成の分割数を既定に戻す。利用者が明示した `--jobs N` は維持する。

## Diag のモデル候補を全区分表示

- `aidiy_codex_models_info.json` は `piModelsInfo` と同じ生成結果が正本。TUI の `model_catalog.rs` は現在の接続先の候補だけでなく、`aidiy_model_presets()` で API / OAuth / 外部 CLI の全対応区分を読み込む。`provider/model` が候補の識別子であり、異なるプロバイダの同名モデルをまとめない。
- CLI で開始した session では、接続先が特定できない区分なしのサーバー既定候補を除外する。API で開始した場合の従来候補は保持する。
- 初回非同期ロード時とキャッシュ表示・再表示で同じマージ処理を使う。サーバーから得た同一 ID の能力メタデータは上書きしない。未対応区分、再帰する AiDiy ハーネス、空 ID、不正ラベルを除外し、CLI の `same` は保持する。
- 検証: `cargo test -p codex-model-provider-info --locked aidiy_cli --lib`、`cargo test -p codex-tui --locked model_catalog::aidiy_tests --lib`、`node --test frontend_diag/checks/codex-info.check.mjs`。一覧の表示だけでプロバイダの接続成功を保証するものではない。

## 外部 CLI メタハーネスの追加

- `model-provider-info/src/aidiy_cli.rs` と `aidiy_sections.rs`：6 CLI 区分の解析、Diag カタログの読取、親に OpenAI 認証を要求しない内部 CLI provider。`lib.rs` から公開する。
- `core/src/aidiy_cli.rs`：Pi / Hermes と共通の `backend_tools/tools_proc/harness_cli.py` を子プロセスで起動。親モードと会話を JSON で渡し、JSONL の進捗・最終回答を `ResponseStream` に変換。サイズ制限、無出力タイムアウト、キャンセルと子孫終了、非再試行エラーを扱う。
- `core/src/session/turn.rs`：API 送信前に CLI 区分へ振り分け、CLI ターンの自動圧縮を止める。`core/src/client.rs`：補助要求から CLI 名を API へ送らない。`core/src/lib.rs`：委譲モジュール登録。
- `tui/src/model_catalog.rs`：Diag の候補を追加。区分付きモデルは API / OAuth / CLI 間で切替可能（接続分離は後述）。
- upstream 更新時は `ResponseItem` / `ResponseEvent` の構造、`ResponseStream` の drop キャンセル、ターンの権限取得、モデルピッカーの更新経路を確認して移植する。CLI の通常失敗を再試行可能な API エラーへ変更しない。

ignore は追跡済みファイルや過去コミットを消さず、既存の GitHub 警告を閉じるものでもない。今回の対応は履歴を書き換えない。再発確認には `python scripts/test_codex_secret_fixtures.py` を使う。

### 変更による動作の違い（upstream との差）

- **マルチプロバイダ:** `--model <区分>/<モデル名>`（openai_oauth / openai_chat / xai_oauth / claude_chat / gemini_chat / freeai_chat / openrt_chat / openrt_free / ollama_chat / local_chat）で、Hermes / Pi と同じ接続先へつなぐ。`--provider` などの指定や `model_provider` の選択肢は増やさない。区分ごとの接続方式は [AGENTS.md の「区分ごとの接続」](AGENTS.md#区分ごとの接続)。
- **接続方式:** Responses に加え Chat Completions と Anthropic Messages。core の再試行・認証・ツール実行・サンドボックスは upstream のまま。
- **認証:** openai_oauth は upstream の ChatGPT ログイン（`~/.codex`）のまま。他の区分は upstream の設定項目（`experimental_bearer_token`、`http_headers`、`auth` コマンド）へ AiDiy のキーを入れるだけで、upstream の認証処理は変えない。xai_oauth だけ内部名のトークン取得を Rust で行う。
- **送る版番号:** 設定 JSON の `client_version`（既定 `0.169.0`）。サーバーは版でモデルを出し分けるため、`0.0.0` のままでは新しいモデルを使えない。
- **TUIの表示名・ロゴ:** 起動時・状態カードとプレーンテキストの見出しは `AiDiy CODEX`。起動タイトル直下にPi風の2行ロゴ `AiDiy-CODEX` を表示する。AiDiy部分はHermesと同じ黄金色 `#FFD700`、ハイフンはグレー、CODEXは白 `#FFFFFF`（yは同じ高さで裾を左へ曲げた小文字風、Oは四角、大文字Eの中央横棒は上段の下線属性で表現）。
- **変えていないもの:** 表示名・起動ロゴ以外のTUI、ツール、サンドボックス、app-server、`/model` の挙動。

## 最新版への再移行手順

1. **取得:** upstream の最新版を別フォルダへ取得し、`codex-rs/` だけを使う。取り込むコミット ID と日付を控える。
2. **退避:** 現在の `command_codex/codex-rs/` を別名で残す（差分の確認と、追加ファイルの取り出しに使う）。`~/.aidiy/cache/codex/target` は版が変わると再利用できないため、空き容量が足りなければ全体 cleanup で削除する。
3. **差し替え:** `command_codex/codex-rs/` を新しい `codex-rs/` に置き換える。`LICENSE` / `NOTICE` は新しい版のものを使う（AiDiy 側で書き換えない）。
4. **移設:** upstream ルートの `.cargo/config.toml` を `codex-rs/.cargo/config.toml` へ移し、出典コメント（`AiDiy: moved from ...`）を付ける。
5. **追加ファイルを戻す:** 上の「追加したファイル」5つ（テストを含む）を退避した旧版からコピーする。
6. **変更を再適用:** 旧版で `rg -n "AiDiy" codex-rs` に出る箇所を、上の「変更したファイル」の表に沿って新版へ当て直す。upstream 側の構造が変わっていれば、下の「上流の変化に注意する箇所」を見て合わせ直す。
7. **版と依存:** `Cargo.toml` の `[workspace.package] version` を `0.169.0` にし、`model-provider-info/Cargo.toml` に `serde_json` を加えてから `cargo update --workspace --offline` で `Cargo.lock` を合わせる（それ以外の依存は更新しない）。`rust-toolchain.toml` の版が上がった場合は、llvm-mingw で gnullvm ターゲットがビルドできるかを最初に確認する。
8. **確認:** 下の「確認方法」を上から順に行い、終わったら「再移行の記録」に追記する。

## 上流の変化に注意する箇所

再移行で壊れやすい、upstream の構造に依存している箇所です。

- **`WireApi`（model-provider-info）:** 値の追加・Deserialize の書き方・削除済みエラー定数が変わっていないか。`remote.rs` の proto 対応付けも合わせる。
- **`core/src/client.rs`:** `stream()` の HTTP / WebSocket の振り分けと、HTTP 実行部（`ResponsesHttpExecutor`）の構造。`ResponsesApiRequest` を作る箇所（`model:` を `aidiy_api_model()` にする2か所）。
- **Responses 要求の JSON 形:** Chat / Anthropic の変換は、`ResponsesApiRequest` をシリアライズした JSON の `input` / `tools` と、項目の `type`（`message` / `function_call` / `function_call_output` / `custom_tool_call` / `custom_tool_call_output`、ツールの `function` / `custom` / `namespace`）に依存する。名前や形が変われば変換を直す。
- **`ResponseEvent` / `ResponseItem`:** `Created`、`OutputItemAdded`、`OutputTextDelta`、`OutputItemDone`、`Completed`（`TokenUsage`）と、`FunctionCall`（namespace を含む）・`CustomToolCall` の形。
- **`core/src/config/mod.rs`:** プロバイダ ID の決定順（`required_model_provider`、`model_provider`、`cfg.model_provider`）と `model_providers` の組み立て。
- **モデル情報の検索:** models-manager の `find_model_by_namespaced_suffix()`（`openai_oauth/gpt-…` からモデル情報を引く）が残っているか。無くなった場合は区分を外して検索する処理が要る。
- **app-server の既定モデル置き換え:** `allow_provider_model_fallback` が exec で既定（無効）のままか。有効になると区分付きの名前が既定モデルへ置き換わる。
- **認証:** `external_bearer.rs` の `run_provider_auth_command()`、`login` の `OAuthClient` / `TokenEndpoint` / `create_client()`（`aidiy_grok.rs` が使う）、`ModelProviderAuthInfo` の項目。
- **版番号:** `default_client.rs` の User-Agent と `models-manager` の `client_version_to_whole()`。サーバーが求める最低版が上がった場合は、再ビルドせず設定 JSON の `client_version` を上げて確認できる。
- **モデル一覧の取得条件:** `models_endpoint.rs` の `has_command_auth()` と、models-manager の `should_refresh_models()`。

## 確認方法

Code Mode の補助ホストは `_compile.py` で本体と合わせて用意する。Windows は `aidiy/runtime_tools.py` が固定版 `@openai/codex@0.169.0-win32-<arch>` の公式 npm 配布物からホストだけを取り出す。SHA-512 とパッケージ名・版・URLを照合し、既存ホストの SHA-256 が配置記録と一致する場合は再取得しない。`~/.aidiy/bin/aidiy_codex_runtime.json` に出典と検証値を記録し、元の LICENSE / NOTICE も配置する。本体は従来どおり gnullvm / llvm-mingw でコンパイルし、MSVC 開発環境は導入しない。Linux / macOS は同梱の `codex-code-mode-host` を本体と同時にコンパイルする。確認は `scripts/checks/test_codex_runtime_tools.py`。

`_compile.py` はビルド後、`~/.aidiy/bin/aidiy_codex_temp(.exe)` に配置用の実行ファイルを完成させてから `aidiy_codex(.exe)` と入れ替える。コピー・デバッグ情報除去の途中のファイルは公開しない。本体使用中などで入れ替えに失敗した場合は既存本体と完成済みの一時ファイルを保持し、手動入れ替え先をログに表示して失敗終了する。

`app-server/src/lib.rs` の `loader_overrides_with_test_user_config_file()` は、debug ビルドだけローカル変数を可変にする。テスト用設定の変更を維持し、release ビルドの `unused_mut` 警告を防ぐ（`AiDiy:` コメント）。上流再取り込み時は条件付きコンパイルの両方を確認する。

1. 変更箇所の確認: `rg -n "AiDiy" command_codex/codex-rs --glob '!target'` で、上の表の全ファイルが出ること。
2. 単体テスト（`_compile.py` と同じ環境で。デバッグ成果物が十数 GB 増えるので、終わったら `~/.aidiy/cache/codex/target/<target>/debug` を消す）:
   - `cargo test -p codex-model-provider-info aidiy` と `cargo test -p codex-model-provider-info chat_wire_api`
   - `cargo test -p codex-api chat_completions` と `cargo test -p codex-api anthropic`
   - `cargo test -p codex-login aidiy`
   - `cargo test -p codex-model-provider models_endpoint`
3. AiDiy 側: `python -m unittest scripts/checks/test_setup_codex.py scripts/checks/test_codex_compile_cancel.py`、`node --test frontend_diag/checks/codex-info.check.mjs frontend_diag/checks/models-info.check.mjs`。
4. ビルド: `python command_codex/_compile.py --yes`（release）。`aidiy_codex --version` が `codex-cli 0.169.0` であること。
5. 実接続（有料 API を含むため、利用者の了承を得て区分ごとに 1 回だけ）: `aidiy_codex exec --skip-git-repo-check --sandbox read-only --ephemeral -m <区分>/<モデル名> "Reply with the single word OK."` を各区分で実行し、`OK` が返ること。キー・トークンは表示・記録しない。

## CLI chat / passthrough 切替

`--cli chat`（省略時）と `--cli passthrough` を追加。後者は従来の子CLI委譲を維持する。chat は会話・ツール定義・ツール結果を構造化して共通アダプターに渡し、返されたツール要求を親Codexの通常ツールループへ戻す。親のsandbox・承認は親が適用する。子CLIがchat方式を安全に提供できない場合は共通アダプターが停止し、委譲へ暗黙に切り替えない。

`core/src/aidiy_cli.rs`、`cli/src/main.rs`、`codex-api` の `CliChatCodec` が対象。namespace/customツールは既存Chat Completions変換器を再利用し、自由形式ツールも元の形式へ戻す。構造化最終出力・画像音声は引き続き対象外。起動引数はプロセス内だけに適用し、ユーザー設定を書き換えない。

`checks/cli_chat_codec_smoke.py` は実ソースから変換器・応答検証を抽出し、軽量Rustクレートで挨拶、親ツール結果の往復、namespace/custom復元、不正応答拒否を確認する。V8依存なしで実行できるが、ResponseItem/ResponseEventは試験用の簡略型であり、Codex全体の型検査・実CLI試験を代替しない。`cargo test --locked -p codex-api cli_chat_tests --lib` とCLI/core側のテストは別途必要。応答の `tool_calls` が配列以外、`content` が文字列/null以外なら、テキストが併記されていても不正応答として停止する。


## 単体配置時の TUI 起動と先行ランチャー登録

AiDiy は単体の `aidiy_codex(.exe)` と実行用補助ファイルを配置するため、upstream の `codex-package.json` を要求する共有 daemon の自動導入は利用しない。`tui/src/daemon_startup.rs` の既定除外により組込みハーネスで実行し、インストール済み公式 Codex の daemon にも自動接続しない。明示 `--remote` は通常どおり扱う。再移行時はこの方針と `daemon_startup_tests.rs` を維持する。

全体 `_setup.py` は、コンパイルを選択しない場合も `_compile.py` の `install_standalone_launcher()` で共有・プロジェクト別ランチャーを作成する。依存の取得やコンパイルはこの登録処理では行わない。起動引数と作業ディレクトリを保ち、実行先は `~/.aidiy/bin/aidiy_codex(.exe)` に固定する。検証: `python -m unittest discover -s scripts/checks -p 'test_setup_codex.py'`。

## AiDiy: 会話中の API / CLI プロバイダ切替

- `core/src/client.rs` はモデル区分から接続先・認証方式を再解決し、provider 変更時に独立した client を作る。旧 provider の接続、sticky routing、固有ヘッダー、認証状態を新 provider に引き継がない。
- `session/turn_context.rs`、`session/turn.rs`、`session/startup_prewarm.rs`、`compact*.rs` で通常推論・prewarm・圧縮の接続先を揃える。API / OAuth / CLI の行き来が可能。
- HTTP / WebSocket 送信前に区分と provider を検証する。CLI を API へ送らない。管理者必須 provider / runtime 認証を回避して切り替えない。
- `client_tests.rs` の `aidiy_` テストは API 間 / CLI→API / OAuth 復帰の認証と接続分離、不一致拒否を確認する。

### CLI chat のテキスト JSON ラッパー

- `core/src/aidiy_cli_json.rs` が親 Rust 側で回答 JSON の説明と例を付加し、CLI のテキスト回答の最初の `{` から最後の `}` を抽出する。子 CLI に JSON schema 出力機能を要求しない。
- JSON は再帰的な重複キー検査を伴って厳格に解析する。複数 object・途中切れ・不正 JSON はツールとして実行しない。
- 抽出後は `harness_cli.py` の `validate_chat` を検証専用として呼び、既存の応答 schema・登録ツール名・引数 schema 検証を必須で通す。検証失敗・起動失敗では停止する。実際のツール実行と承認は親 Codex のまま。
- 移植時は `aidiy_cli.rs` の `engine_prompt` 送信、生テキスト応答のラッパー呼び出し、検証専用呼び出しをセットで維持する。passthrough は変更しない。

- JSON 構文修正の1回再試行では、実際の失敗応答を非信頼データとしてJSON文字列で引用し、その後に必要な応答形式と引数規則を再掲する。65536 Unicode文字を超える失敗応答は切り詰めず停止する。生応答を診断ログへ出さない。ルーティング、キャンセル、schema検証、認証・実行失敗時の停止は維持する。
