ポイント: デュアルサーバー構成

業務画面(C/M/T/V/S/A系)のバックエンドは2つのサーバーで構成されます
• Core API (8091): C系（共通管理）とA系（AI機能）を担当
• Apps API (8098): M系（マスタ）、T系（トランザクション）、V系（ビュー）、S系（スケジューラー）を担当

補足: 実際の常駐サーバーは5つ

このガイドはCore/Apps/Web/Avatarを中心に解説しますが、現行リポジトリには次のサーバーも存在します。

  • backend_tools/tools_main.py (8095) — Chrome操作、DB確認、メディア生成、Task/Team Agents、Windows操作など19個のMCPとOpenAI/Ollama互換Chat Completions
  • backend_taskteam/taskteam_main.py (8093) — AIタスク要求の分解・実行、定期タスク、複数AIエージェントのチーム活動を同一プロセスで管理
  • backend_local/local_main.py (8096) — OpenAI互換のローカルLLM(Gemma)推論。_start.pyの既定では起動しない

また command_hermes(aidiy_hermes)というコード支援CLIもあるが、常駐サーバーではなく_start.pyの起動対象外。詳細は各フォルダの AGENTS.md を参照してください。

なぜこの技術スタックか

選定理由

  • FastAPIはOpenAPIドキュメントを自動生成できる
  • PythonとSQLAlchemyの組み合わせで日本語カラム名が使える
  • Vue 3のComposition APIで画面ごとのロジックを整理しやすい

プロキシ設定について

フロントエンドからのAPIリクエストはプロキシ経由で転送されます。

  • /core → 8091、/apps → 8098、/task・/team → 8093、/mcp → 8095 に転送
  • /mcp は転送時にprefixを除去する。Avatar側には /mcp proxyはない
  • 業務CRUDのAPI操作は原則POSTメソッドを使用

詳細は frontend_web/vite.config.ts を参照してください。

CORS許可オリジン

backend_server/core_main.py と apps_main.py で以下のオリジンが許可されています。

  • http://127.0.0.1:8090 — Vite本番開発サーバー
  • http://127.0.0.1:5173 — Viteデフォルトポート
  • http://127.0.0.1:3000 — 代替ポート
ポート変更時の注意

フロントエンドのポートを変更する場合、frontend_web/vite.config.ts または frontend_avatar/vite.config.mts の server.port だけでなく、 以下の設定も連動して更新する必要があります。

  • backend_server/core_main.py の CORS 許可リスト
  • backend_server/apps_main.py の CORS 許可リスト
  • _start.py のポート設定

データフロー

リクエストがどのように処理されるかを説明します。

一覧取得の流れ（例）

  1. ユーザー操作: ブラウザで一覧画面を開く
  2. Vue コンポーネント: C利用者一覧.vue がAPI呼び出しを実行
  3. Viteプロキシ: /core/C利用者/一覧 → 127.0.0.1:8091/core/C利用者/一覧 へ転送
  4. FastAPI Router: core_router/C利用者.py がPOSTリクエストを受信
  5. 認証チェック: JWTトークンを検証
  6. CRUD処理: core_crud/C利用者.py がデータベースを検索
  7. SQLite: SQLクエリを実行して結果を返却
  8. Response: JSON形式で返却 {"status": "OK", "data": {"items": [...], "total": N}}
  9. Vue コンポーネント: 受信したデータを画面に表示
API設計の注意点
  • 全てのAPI操作はPOSTメソッドのみ（GET・PUT・DELETEは使わない）
  • レスポンス形式は統一: {"status": "OK"/"NG", "message": "...", "data": {...}}
  • Serviceレイヤーは原則無し。RouterからCRUDを直接呼び出す
  • 一覧の上限は10000件

APIルーティングの流れ

Core系とApps系でリクエストの流れが分かれます。

[例1: Core系]
[フロント] → /core/C利用者/一覧
   ↓
[core_router] → [core_crud] → [core_models] → SQLite

[例2: Apps系]
[フロント] → /apps/V商品/一覧
   ↓
[apps_router] → [apps_crud or 生SQL] → [apps_models] → SQLite

送信先の判断

テーブル名の先頭文字で送信先が決まります。

サーバー ポート パス 対象テーブル
Core 8091 /core/* C系 (C権限, C利用者, C採番) / A系 (AIコア, A会話履歴)
Apps 8098 /apps/* M系 (M商品, M車両, M配車区分) / T系 (T配車, T商品入庫等) / V系 / S系
Task / Team 8093 /task/* / /team/* Aタスク要求/明細、定期タスク、AIチーム依頼・会話・作業
迷ったら
  1. テーブル名の先頭文字 (C/A/M/T/V/S) を見る
  2. C系とAIコア/A会話履歴は /core、M/T/V/S系は /apps、AIタスク・AIチームは /task / /team
  3. 一覧APIで先に疎通確認する
