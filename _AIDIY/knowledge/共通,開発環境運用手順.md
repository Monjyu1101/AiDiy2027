## モジュール別の実行環境

`_setup.py` / `_start.py` / `_cleanup.py` は Python の管理入口です。対象アプリの実行条件と、管理入口を動かす Python の版は分けて考えます。全体構成の Node.js は 22.13 以降を推奨し、個別条件は各 manifest と導入済み依存（未導入時は lockfile）の `engines` を参照します。依存版を一括で同じにしたり、警告を消すためだけに更新したりしません。

| 対象 | 実行環境・画面 | 条件と意図した違い |
|---|---|---|
| Local / Core・Apps / Tools / TaskTeam / Hermes | Python / uv | 各 `pyproject.toml` の `requires-python` は現在 `>=3.13`。setup は uv の Python 選択に委譲し、start は選択された venv の実行可否と版数を確認する |
| Diag | Node.js / Vue 3 配布画面 / Electron または Web | 診断本体・headless・Web は Node.js 18 以降。Electron 44 の npm 依存は Node.js 22.12 以降。Python は管理入口で使用し、配置済みランチャー・直接 Node 起動には不要。VS Code 不要 |
| Web | Node.js / Vue 3 / Vite / TypeScript | Vite 8 の条件は `^20.19.0 || >=22.12.0`。Node.js 21 は範囲外。Electron / VS Code 不要 |
| Avatar | Node.js / Vue 3 / Vite / TypeScript / Electron または Web | Vite 条件に加え、Electron 44 の npm 依存は Node.js 22.12 以降 |
| IDE / Console / Task / Team / Browser | Node.js / Vue 3 共通画面 / Electron または Web | viewer の `engines.node` は `>=22.13`。Browser は Electron 必須、ほかの Web 対応画面を同じ条件で止めない |
| Code / Live (host) | Node.js / Vue 3 共通画面 / TypeScript / Electron または Web / VS Code 拡張 | 拡張の `engines.vscode` は `^1.106.0`。単独 Electron / Web に VS Code は不要。VSIX 用 vsce には Node.js 22 以降、Electron 44 には 22.12 以降が必要 |
| Discord (channels) | Node.js / Vue 3 接続パネル / TypeScript / Electron または Web | `engines.node` は `>=22.12.0`。セットアップは画面コンパイルにも使う devDependencies を含めて導入する。VS Code 不要 |

- 新規の版数チェックは、宣言範囲外・版数や metadata の判定不能を警告して続行します。未導入・実行不能・確認 timeout は区別してエラーにし、実際の import / npm / runtime の失敗も握りつぶしません。既存の Diag Node.js 18 未満停止は維持します。警告継続は互換性保証ではありません。
- Electron / Vue 3 は各 npm プロジェクトの依存です。グローバル Electron / Vue CLI の導入は要求しません。Electron は既存の共有バイナリ準備経路を使い、Web 対応の Code / Live・Discord は Electron が未準備でも Web へ切り替えられます。
- Hermes のルート `package.json` は upstream の Node/workspace 開発用です。AiDiy の Python CLI 起動条件へ混ぜません。Tools の Python MCP 自体にも Node.js を追加要求しません。
- 復旧は表示された対象モジュールの `_setup.py` を使います。依存の不足と版数警告を混同せず、単純な `npm install` だけで共通 UI・ランチャーの準備が完了すると案内しません。
- cleanup には新しい版数・venv の存在を前提にしません。実行可能な管理用 Python は必要です。Node.js / npm は選択したグローバル npm 登録の解除、VS Code CLI は選択した拡張解除でのみ使用します。各モジュールの環境・生成物・登録を選択に従って整理し、OS の Python / Node.js / VS Code 本体や共通設定を勝手に削除しません。DB 削除は従来どおり明示選択です。
- cleanup の削除・解除失敗はモジュールからまとめ役へ返し、失敗箇所と終了コード 1 を維持します。Diag の配布画面を残す方針や Code / Live の拡張解除を確認できないときに生成物を残す方針など、復旧上必要な違いは維持します。試験は一時ディレクトリの fixture / mock で行い、実開発環境を削除しません。

## 起動手順

通常起動はプロジェクトルートで行う。

```powershell
python _start.py
```

`_start.py` は対話形式で、起動するサービスを選択する。`backend_local` はデフォルト No。未起動時は AI設定の `local_chat` 候補から除外される。`command_hermes` は on-demand CLI のため常駐起動対象ではない。`frontend_channels/discord` / `frontend_channels/slack` は既定 No で、Yes の場合は接続パネルを開いて自動接続する。

フロントエンドは Avatar の直後に `aidiy_task [n]/y` → `aidiy_team [n]/y` を個別選択する（両方とも既定 No、`y` の場合だけ起動）。TaskTeam バックエンドは従来どおり先に起動し、Task / Team 画面だけの選択でバックエンドの選択を変更しない。その後「IDE群(Console / Code / Live / IDE)」で Console → Code → Live → IDE を個別選択し、その後に Discord、Slack を選択する（いずれも既定 No）。セットアップ・cleanup はIDE群を一括選択（既定 Yes）し、`frontend_ide/_setup.py` / `_cleanup.py` が Code / Live のhost → IDEのviewer → 共通UIを管理する。Discord・Slack は Channels (Discord / Slack) の1項目としてその後に一括選択・実行する（既定 Yes）。ルートの選択キーは `channels` とし、内部の停止照合・依存導入・設定補完は既存の各機能へ委譲する。各フォルダのスクリプトを直接実行する場合は従来どおり個別処理とする。`frontend_ide/host/_start.py` は `aidiy_code` / `aidiy_live` と同じランチャーをコマンド起動し、作業フォルダはプロジェクトルートにする。Code は待機指定を付けず独立起動し、Live は `--foreground --connect` を渡す。Live はモデル未指定でも保存済み選択（未保存なら Core の既定設定）で1回だけ自動接続し、マイクは OFF のまま。手動で閉じた画面は自動再表示しない。全体起動の終了後も Code / IDE / Discord / Slack は継続し、明示的な cleanup では子プロセスも回収する。

個別起動が必要な場合:

通信サイズの基準は **20 MiB（20 × 1024 × 1024 = 20,971,520 bytes）**。
Backend の標準起動入口は Uvicorn の WebSocket 上限をこの値にする。
`UVICORN_WS_MAX_SIZE` が明示されている場合は、その値を優先する（小さい明示値も上書きしない）。
手動で `uvicorn` を実行するときは下記の `--ws-max-size` を付ける。未指定の Uvicorn 自体の既定は 16 MiB であり、FastAPI の全 HTTP body に一律の 20 MiB 上限があるわけではない。
Tools の管理・内部 Prediction/Live 試行 JSON の既存受信上限と OBS の受信 WebSocket は 20 MiB、Chrome CDP は従来の 50 MiB を維持する。
元々制限のない HTTP 経路へ新しい制限を加えず、認証 header・prompt/パス等の項目検証、設定ファイルや生成画像の読込上限は通信サイズとは別に維持する。

```powershell
# Core API
Set-Location backend_server
.venv/Scripts/python.exe -m uvicorn core_main:app --reload --host 0.0.0.0 --port 8091 --ws-max-size 20971520

# Apps API
Set-Location backend_server
.venv/Scripts/python.exe -m uvicorn apps_main:app --reload --host 0.0.0.0 --port 8098 --ws-max-size 20971520

# MCP
Set-Location backend_tools
.venv/Scripts/python.exe tools_main.py

# TaskTeam（`/task/*` と `/team/*`）
Set-Location backend_taskteam
.venv/Scripts/python.exe -m uvicorn taskteam_main:app --reload --host 0.0.0.0 --port 8093 --ws-max-size 20971520

# Hermes CLI
Set-Location command_hermes
.venv/Scripts/python.exe cli_main.py

# frontend_web
Set-Location frontend_web
npm run dev

# frontend_avatar
aidiy_avatar

# frontend_channels/discord
aidiy_discord
```

アバターの `aidiy_avatar` は既存の Electron / Vite 起動処理を使い、どの作業フォルダからでも実行できる。Ctrl+C でアバターを停止する。`python frontend_avatar/_setup.py` で AiDiy 本体の `_AIDIY/aidiy_avatar/bin` に登録する。依存関係を更新せずランチャーだけ登録する場合は `python frontend_avatar/_setup.py --launchers-only` を使う。`aidiy_avatar --help` は画面やサービスを起動せず使い方を表示する。

`aidiy_avatar` / `aidiy_live` / `aidiy_discord` / `aidiy_slack` は二重起動を防止する。再実行で既存の画面・接続・モデルを作り直さない。Avatar は起動処理を OS のファイルロックで排他し、8092 が起動中なら停止せず終了する。Electron 側でも単一起動にする。Live / Discord / Slack は GUI・ブラウザ共通のローカル排他（18094 / 18095 / 18096）を持ち、画面がある場合は再表示する。排他はプロセス終了時に OS が解放するため、強制終了後も手作業でロックを削除する必要はない。

## setup / start / cleanup の停止方針

目的: 開発中も外部から Discord / Slack 経由の調整依頼を受け付け続けるため、Discord / Slack を Code / IDE と同じ継続対象にする。setup / start の一括強制終了で受付窓口や、その依頼を処理する CLI / MCP 子プロセスを閉じない。Core 等の停止中もすべての機能が使えるという意味ではなく、特に Live は Core に依存する。明示的な cleanup や利用者が選んだ個別停止・終了は別扱いとする。

- 通常の `_setup.py` と `_start.py` は開始選択の承認後、この配置先の AiDiy プロセスを一度だけ停止する。`aidiy_code` / `aidiy_ide` / `aidiy_discord` / `aidiy_slack` と必要な補助プロセスは維持する。
- Live / Avatar だけの特別扱いはしない。Diag、Local、Tools、Core / Apps、Task / Team、Web、Avatar、Hermes、Console、Live と確認できる実行を共通処理で停止する。
- IDE / Code / Discord / Slack の子として起動された独立した Live / Console 等は停止対象。renderer や MCP など、継続画面に必要な子は保護する。
- `_start.py` のサービス起動直前には停止を重ねない。setup は start を自動実行しないため、別コマンドとして起動した start は独立して一度確認する。以前のsetupを理由に停止確認を永続的に省略しない。
- `_cleanup.py` は従来どおり Code / IDE / Discord / Slack を含む全停止。今回の保持方針をcleanupへ適用しない。
- `scripts/_setup_processes.py` は実行入口・専用実行環境・親子関係を照合し、ポート番号だけやプロセス名の部分一致では停止しない。setup / start 自身と起動元の祖先は停止しない。Windowsでも `/T` による保護対象の巻き込みを避ける。
- 他の配置先や、所有元の確認できない共有Electronの孤児等は推測で停止しない。実行中プロセスの情報を取得できない場合や、確認済み対象が残る場合はsetup / startを中止する。Windowsの相対入口は専用実行環境で所属を判断する。新しいstartはPIDとプロセス作成日時を含む所有記録を一時保存し、相対 `_start.py` も識別する。旧版等の所属不明な監視親が対象を再起動し得る場合は、先にその監視を終了するよう案内して中止する。判断できない単独プロセスは対象外。
- Code / IDE / Discord / Slack の画面は残るが、Core等の停止中はサーバー接続機能が一時的に使えない。
- Discord / Slack は `frontend_channels` 配下として、本体・専用Electron・CLI / MCP 子孫を共通の停止対象選択で保護する。通常は起動中または稼働状態を確認できない場合、各 `_setup.py` は npm・ランチャー・共通設定を変更せず `False` で更新を保留する。
- 一括setupで「エラーが発生しても続行」を選択した場合は、起動中でも停止せず各工程を一度ずつ試行する。Electron 本体のコピー・配置の `OSError` は WARN（入力欠損は除外）として別集計し、配置未確認であることを表示する。npm・ビルド・取得・検証等の失敗は NG のまま後続を試行し、最終結果も失敗とする。コピー警告だけなら警告付き終了となる。更新中の画面の継続動作は保証しない。確実に更新する場合は保存して画面を閉じ、setupを再実行する。

## バックエンド変更の反映

`_start.py` 起動では uvicorn に `--reload` が付かない。コード変更を反映する場合は、次のいずれかを使う。

```powershell
# core_main.py を再起動
New-Item -ItemType File -Force backend_server/temp/reboot_core.txt

# apps_main.py を再起動
New-Item -ItemType File -Force backend_server/temp/reboot_apps.txt

# taskteam_main.py を再起動
New-Item -ItemType File -Force backend_taskteam/temp/reboot_taskteam.txt

# tools_main.py（MCP 8095）を再起動
New-Item -ItemType File -Force backend_tools/temp/reboot_tools.txt

# local_main.py（8096）を再起動
New-Item -ItemType File -Force backend_local/temp/reboot_local.txt
```

各サーバーは自分の `temp/reboot_*.txt` を1秒ごとに監視し、検知するとファイルを削除して終了する。`_start.py` が終了を検知し、15秒後に同じコマンドで起動し直す。AIコアの設定変更で再起動が必要な場合も、同じファイルを書いて再起動する。プロセスを直接終了しても自動再起動されるが、子プロセスごと止まるため reboot ファイルを優先する。backend_tools の `pyproject.toml` に依存を追加した場合は、`uv sync` の後に tools を再起動する。

または個別起動で `--reload` を使う。

## 初期セットアップ

初回または環境リセット時:

```powershell
python _setup.py
```

「エラーが発生しても続行」は、失敗した後も残りの項目を実行する指定です。失敗を成功扱いにはせず、最後にエラー発生場所を表示して終了コード `1` を返します。すべて成功した場合だけ正常終了（終了コード `0`）になります。HTTP 403 などで依存更新に失敗した場合も、導入済みの別項目やビルドの成功だけで全体成功とは判定しません。続行しない場合は失敗箇所で停止します。

Git / Node.js の前提確認に失敗した場合は、続行指定でも後続の導入を開始せず終了コード `1` で停止します。AI CLI を導入する選択では、インストーラー準備失敗・プロセス起動失敗・導入中の失敗をパッケージ別に集計します。一部の起動に失敗しても、既に起動した導入処理の結果を待ってから最終判定します。通信や実導入を行わない回帰確認は `python -B -X utf8 scripts/checks/test_setup_result.py` を使います。

主な対象:

- `backend_server` の Python 仮想環境と依存関係。
- `backend_tools` の Python 仮想環境と依存関係。
- `command_hermes` の Python 仮想環境と依存関係。
- `backend_taskteam` の Python 仮想環境と依存関係。
- `frontend_web` / `frontend_avatar` の `npm install` と `npm update`。
- `frontend_ide/host` の依存導入、Electron の準備、Code / Live の VSIX 生成と VS Code 拡張機能への配置、`_AIDIY/aidiy_code/bin` / `_AIDIY/aidiy_live/bin` へのランチャー作成。VS Code CLI が無い場合は単独起動用のコンパイルとランチャー作成だけを行う。ルート選択では `command_hermes` の次に実行する。
- Channels (Discord / Slack) は既定 Yes の1項目で、`frontend_channels/discord` と `frontend_channels/slack` の依存導入、Electron の準備、接続パネルのビルド、`aidiy_discord` / `aidiy_slack` ランチャー作成、共通設定の不足キー補完を行う。`continue_on_error=False` では最初の失敗で停止し、True では両方を試して機能別の失敗をまとめる。Electron 配置の警告は両方の処理を通じて保持する。

### プロジェクト内ランチャーと PATH（全 OS 共通）

Hermes を除くランチャーは AiDiy 本体の `_AIDIY/aidiy_<pg>/bin/` に配置する。例: `_AIDIY/aidiy_diag/bin/aidiy_diag`（Windows は `.cmd`）。空のプロジェクト指定は AiDiy 本体を意味する。ホーム配下への配置・旧配置の参照へのフォールバックは行わない。

Windowsでは通常の `python _setup.py` が選択した各アプリのプロジェクト内binをユーザーPATHへ登録する。CPUはIDE群に含まれ、Browser / Consoleと同じ登録処理を使う。別の復旧プログラムや手動のPATH設定は不要。ランチャー本体と登録記録はプロジェクト内に保ち、ホーム配下へ新たなランチャーは作らない。

- 既存のユーザーPATHの文字列・順序・型を保持し、未登録のフォルダだけを追加する。大文字小文字や区切り文字の違いを正規化して重複を避ける。システムPATHや、セットアッププロセスだけにある項目をユーザーPATHへコピーしない。
- PATH登録に失敗した場合はセットアップを失敗として報告する。成功後は、cmdを含むターミナルやVS Codeを開き直してコマンドを実行する。既に開いている親プロセスの環境変数は変更できないため、既存のターミナルから子cmdを開くだけでは反映されない場合がある。反映されなければWindowsへサインインし直す。
- cleanupはそのbinが空になった場合だけ、setupが追加したPATH項目を解除する。利用者が以前から登録していた項目や、後から加えた別のPATHは残す。既存のホーム配下ランチャーも移動・削除しない。

Linux / macOSでは、Hermesを除いてセットアッププロセスとその子のPATHだけを変更する。シェルプロファイルは変更しない。別ターミナルではフルパスで起動するか、セットアップが表示する現在のシェル限定のPATH設定を実行する。新しいターミナルを開くだけではPATHは登録されない。

回帰確認は `python -B -X utf8 -m unittest scripts.checks.test_setup_path scripts.checks.test_setup_posix scripts.checks.test_cpu_launcher`。Windowsは模擬レジストリで通常IDE setupの9コマンド登録・再実行・既存PATH保護・解除を確認し、実ユーザーのレジストリやホームは変更しない。Windows実機でのcmd・Electron起動は別途確認する。

Hermes は従来どおり `~/.local/bin/aidiy_hermes`（Windows は `.cmd`）に配置し、シェルプロファイルまたは Windows のユーザー PATH に永続登録する。cleanup では同じ共有 bin に他のコマンドが残っている間は登録を保持し、空になった場合に自動追加した登録だけを解除する。プロジェクト内の bin へ移行しない。

Console のシェル履歴は選択プロジェクトの `_AIDIY/aidiy_console/` に保存する。bash / zsh / sh と PowerShell を対象とし、ユーザープロファイルは読み込まないため、そこで定義した alias・関数・PATH は使えない。親から継承した PATH と外部 CLI 認証用の HOME は維持する。未対応シェルは履歴をホームへ戻さずエラーにする。外部 CLI 自身の認証・設定保存先はこの機能では変更しない。

## git pull 後の Node.js 系再ビルド

`python _setup.py` の最初の選択で `b`（build: Node.js系の再ビルド。大文字 `B` も可）を押します。既存の `y`（項目選択）、`n`（中止・既定）、`a`（既定値で全体セットアップ）はそのままです。

`b` は Diag本体/UI、Web、Avatar、IDE共通UI・Code/Liveホスト・ビューア、Discord・Slack の依存を `npm install --include=dev --no-fund --no-audit` で同期します。既存の `node_modules` を一括削除する `npm ci` や、宣言範囲の最新版へ進める `npm update` は行いません。pullされた `package.json` / lockfile の変更や不足依存は同期対象です。Node.js/npmが無ければ終了し、OSツールを自動導入しません。

依存が揃っていても、Diag UI、Web、Avatar、Code/Live/IDE共通UI、Discord・Slackパネルを必ず既存のビルド処理で再生成します。Code/LiveはVS Code CLIがあればVSIXを再生成・配置し、無ければ単独画面をコンパイルします。共通Vueはhostのビルド内で生成し、二重ビルドを避けます。`aidiy_diag` / `aidiy_avatar` / `aidiy_console` / `aidiy_code` / `aidiy_live` / `aidiy_ide` / `aidiy_discord` / `aidiy_navi` / `aidiy_task` / `aidiy_team` / `aidiy_browser` / `aidiy_cpu` / `aidiy_slack` のランチャーも既存処理で再配置します。

Electron本体は既存配置・他画面の同版・共有ZIPを優先して再利用し、不足時のみ取得します。GUIなし、Codespaces、`ELECTRON_SKIP_BINARY_DOWNLOAD=1` では本体の準備を省略します。Python環境・モデル・DB・MCP/Discord設定補完・グローバルAI CLI更新・Diag headlessは実行しません。アプリや常駐サービスも起動しません。Hermes本体の更新はPythonを含む通常セットアップで扱います。

失敗時は項目名を表示して後続を止め、終了コード1を返します。すべて成功したときだけ完了扱いになります。ネットワークを使った実導入なしの検証は `python -B scripts/checks/test_node_refresh.py`、既存経路の回帰は `frontend_diag/checks/check_setup.py` と `frontend_ide/host/checks/test_setup.py` / `frontend_ide/viewer/checks/test_setup.py` を使います。

### Electron の共通セットアップ

`frontend_diag/_setup.py`、`frontend_avatar/_setup.py`、`frontend_ide/host/_setup.py`、`frontend_ide/viewer/_setup.py`、`frontend_channels/discord/_setup.py`、`frontend_channels/slack/_setup.py` は `scripts/_setup_electron.py` を共用する。npm install / update / rebuild と IDE ビューアの npm ci は `ELECTRON_SKIP_BINARY_DOWNLOAD=1` を付け、Electron の取得を共通処理へ集約する。他の依存のインストールスクリプトは通常どおり実行し、`--ignore-scripts` で復旧した場合は Electron の準備後に `npm rebuild` を行う。

IDE ビューアの postinstall で `TypeError: fetch failed` が出た場合は、`frontend_ide/viewer/_setup.py` が共通処理を使う版か確認する。修正済みのソースでは `python frontend_ide/viewer/_setup.py` で依存を再導入し、同じバージョンの配置済みバイナリまたは共有 ZIP を再利用する。Web 専用環境と明示的な `ELECTRON_SKIP_BINARY_DOWNLOAD=1` 指定時は本体を取得しない。共有処理でも取得に失敗する場合は、表示された接続エラーと GitHub リリースへの接続を確認する。

IDE ビューアは `npm ci` の後に `npm update electron`、Discord は `npm ci` の後に `npm run update:electron` を実行し、Electron を宣言範囲内の最新版へ更新してからバイナリを準備する。Discord のラッパーは更新前後の lock を検証し、npm 更新で省略されることがある変更対象外の `opusscript` optional peer を維持する。Avatar / Code・Live は共通処理の `npm install` → `npm update` で更新する。6プロジェクトの指定は `^44.7.0` で、44系のマイナー・パッチ更新を取得し、45系以降への更新は依存範囲を変更して行う。IDE ビューアだけを完全固定に戻したり、更新前にバイナリを準備したりすると、古いロック版を再取得するため注意する。

準備は次の順で行う。

1. 対象プロジェクトの配置済みバイナリを確認し、必要なら `path.txt` だけを修復する。
2. 他のフロントエンド（Diag / Avatar / VS Code / IDE ビューア / Discord / Slack）に同じバージョンがあれば、その `dist` をコピーする。
3. 実行中のOS・CPUに対応する `.aidiy_cache/electron/electron-v<version>-<platform>-<arch>.zip` があれば再展開する。
4. まだ取得されていない場合だけ、GitHub の Electron リリース ZIP を Python で取得する。

共有キャッシュはプロジェクト直下の `.aidiy_cache/electron/` に固定し、実行時のカレントディレクトリによらず、全体・各コンポーネント単独のセットアップで共用する。Git 管理対象外とする。旧 `_cache/electron/` は自動移動・削除しない。

ZIP は取得完了後に共有キャッシュへ保存する。バージョンが異なるものや未完了の ZIP は再利用しない。各プロジェクトの `dist` は別々に配置し、一方の更新・削除が他方の実行ファイルへ影響しないようにする。接続・読み取りのタイムアウトは30秒、取得中は約2秒間隔で取得量と速度を表示する。バイナリ取得の自動再試行は行わない。共有 ZIP は `node_modules` の削除後も残るため、再セットアップ時に利用できる。

macOS の Python で `CERTIFICATE_VERIFY_FAILED` になった場合だけ、証明書を検証する `curl` へ取得方法を切り替える。HTTPS のまま取得し、curl の設定ファイルによる検証無効化も引き継がない。通信切断・HTTP エラーを無条件に繰り返す処理ではない。curl も失敗した場合は共有 ZIP を置き換えず終了する。curl がない環境では、Mac は Python 付属の `Install Certificates.command`、Linux は CA 証明書の導入状態を確認する。証明書検証を無効にして回避しない。

ZIP は Python でリンク構造と各ファイルの権限を保持して展開する。`unzip` は不要。macOS の Framework のリンク、Linux の `chrome_crashpad_handler` / `chrome-sandbox` の実行権限を維持し、別画面へのコピーでも保持する。ZIP 内のリンクやパスが展開先の外へ出る場合は中止する。macOS は Intel / Apple Silicon、Linux は x64 / arm64 の資産名を使う。未知の CPU を x64 と見なして取得しない。

Diag の導入に失敗した場合は修正済みのソースで `python3 frontend_diag/_setup.py` を再実行する。`python3 _setup.py --launchers-only` は Electron 本体の修復を行わない。Linux の GUI なし環境は本体導入を省略し、`aidiy_diag --browser` を使う。OS の GUI ライブラリやサンドボックス設定による起動失敗は、ZIP の配置完了とは分けて確認する。

Electron の依存範囲は6プロジェクトの `package.json` でそろえ、更新時は各 `package-lock.json` の解決バージョンもそろえる。ZIP は実行中のOS・CPUで必要になったときだけ取得し、使わないOS向けを先にダウンロードしない。Windowsで使うだけならMac・Linux向けのキャッシュは不要で、削除してよい。別のOSでセットアップする際に、その環境向けを必要に応じて取得する。セットアップでは既存の共有 ZIP を一括削除せず、利用する版を再利用する。壊れた同名 ZIP も先に削除せず、再取得と検証が成功してから置き換える。取得失敗時は既存ファイルを保持する。キャッシュに新しい版があっても、npm パッケージと異なる版のバイナリだけを流用せず、先に npm でバージョンを揃える。

共通処理の確認:

```powershell
python -m unittest discover -s frontend_ide/host/checks -p test_setup.py
python -m unittest discover -s frontend_ide/viewer/checks -p test_setup.py
python3 -B -X utf8 scripts/checks/test_setup_electron_posix.py
```

本番の Electron 起動入口は5か所で、表示するアプリは次の12種類です。旧 Code / Live / IDE のランチャーも現在の `frontend_ide/desktop.cjs` に合流します。

## クリーンアップ

旧Task／Teamなど、常駐アプリから撤去した実装を整理するときも、先に全AiDiyプロセスを停止し、対象コンポーネントのcleanupを実施する。停止確認前に使用中の依存物や生成物を削除しない。Web／Avatarの旧実装整理ではDB・設定・利用者バックアップを削除対象に含めない。cleanup後はロックファイルに従って依存関係を戻し、AvatarのElectron実行出力と起動ランチャーも復元してから、旧入口の不在・型チェック・実起動と終了を確認する。

不要な仮想環境、`node_modules`、`dist`、キャッシュ、DB を整理する場合:

```powershell
python _cleanup.py
```

削除対象は対話形式で確認される。ルート `.aidiy_backup/` や DB を消す場合は復旧材料が不要か確認する。

何らかのクリーンアップを選ぶと、ファイル削除へ入る前に全常駐サービスの `_start.py` 停止処理が呼ばれる。停止対象は Web `8090`、Core `8091`、Avatar `8092`、TaskTeam `8093`、Tools `8095`、Local `8096`、Apps `8098` で、選択した削除対象だけには限定しない。Avatar の残留 Electron プロセスと、待受ポートを持たない Discord Bot（`discord_processes.py` で実行入口を照合）も停止する。ルート `_start.py` が監視中の場合は、全常駐サービスを自動再起動対象から外し、クリーンアップ中や完了直後に再起動しないようにする。

Diagもランチャー解除の選択に関係なく、全体cleanupの削除前に停止・終了確認する。`frontend_diag/diag/起動/プロセス停止.py` はこの作業コピーの `diag_main.mjs`・Electron起動入口と専用Electronの実行パスを照合し、`--require` 付き起動や親を失ったGPU・renderer・utilityも回収する。別コピー・一般ブラウザ・他スクリプトの引数に含まれるだけのDiagパスは対象外。終了確認に失敗したら他サービスの停止を続けたうえでファイル削除を中止する。個別の `frontend_diag/_cleanup.py` も終了確認後にランチャーを解除する。setup / start の停止方針は上記の専用節を参照する。回帰確認は `python -B -m unittest discover -s frontend_diag/checks -p test_cleanup_processes.py -v` で実行する。

全体の `_cleanup.py` は、最後に全階層の `temp`・`_temp`・`.temp`・`tmp` をまとめて削除する。名前は大文字・小文字を区別せず完全一致で判定し、Git管理情報・保存版・リンク先は巡回しない。

## 一度しか使わないスクリプトの置き場所

画像の変換や一括置換など、一度だけ使う Python などのスクリプトは `temp/`（作業するサブプロジェクト直下の `temp/` またはルート `temp/`）に作る。`temp/` は全階層で Git 管理外で、`_cleanup.py` の削除対象になる。

- ソースフォルダに残すのは、再実行の手順として文書に書く常設ツールだけにする。
- Node.js のプロジェクト（`frontend_diag/ui`、`frontend_*` など）の中に Python スクリプトを置かない。どちらの環境で動かすのか迷う原因になる。

## DB 管理

DB ファイル:

```text
_data/AiDiy/database.db
```

開発用に全テーブルを作り直す場合は、利用者が保持要否を判断して手動で行う。アプリ起動や検証処理には DB 削除を組み込まない。保持が必要なデータは事前に退避する。

1. `_start.py` や個別起動中のサーバーを停止する。
2. SQLite Browser / DBeaver など DB 接続ツールを閉じる。
3. `_data/AiDiy/database.db` を削除する。
4. backend を再起動する。

初期データは、対象レコードが未存在の場合のみ投入される。既存DBでは自動更新されない。

旧スキーマへの自動移行・互換フォールバックは行わない。スキーマ変更と手動 DB 再作成の前提は [`backend_server,スキーマ変更手順.md`](./backend_server,スキーマ変更手順.md) を参照する。

## 起動ログの確認

- `_start.py` は子プロセスの出力を行単位でUTF-8デコードし、サービス名を行頭に1回付ける。読み取りの1024バイト境界で日本語をデコードしたり、行途中にサービス名を挿入したりしない。確認は `python -X utf8 -m unittest discover -s scripts/checks -p "test_start_*.py"` で行う。
- ffmpeg / ffprobe / ffplay の未インストール、OBS の未起動、任意のAIベンダーのAPIキー未設定は、それぞれの機能が利用できないことを示す。使わない機能の導入・設定は不要。

## 自動テスト

現行実装には以下のテストがある。テストは各コンポーネントの `checks/` に置き、`tests/` ディレクトリは使わない。`backend_tools/checks/` と `backend_taskteam/checks/` にも Python の回帰テストがある。変更対象に関係するものを選び、Python は対象プロジェクトの依存を導入した環境で実行する。Node.js テストは該当フロントエンドの `npm install` が前提。

| 対象 | 実行ディレクトリ | コマンド |
|------|------------------|----------|
| AIコア（生成ファイル・入力保存・プレビュー・Live）・バックアップ・予測 | `backend_server` | `python -X utf8 -m unittest discover -s checks -v` |
| Tools の設定・認証・転送制限 | プロジェクトルート | `python -X utf8 -m unittest discover -s backend_tools/checks -v` |
| TaskTeam の内部認証・認証永続化 | プロジェクトルート | `python -X utf8 -m unittest discover -s backend_taskteam/checks -v` |
| Hermes の YOLO 削除承認 | プロジェクトルート | `command_hermes/.venv/bin/python -X utf8 -m unittest discover -s command_hermes/checks -v`（Windows は `.venv/Scripts/python.exe`） |
| セットアップ・起動・停止・Task / Team・予測経路 | プロジェクトルート | `python -X utf8 -m unittest discover -s scripts/checks` |
| 環境診断（Diag） | プロジェクトルート | `node --test frontend_diag/checks/*.check.mjs frontend_diag/checks/*.check.cjs` |
| Console / Code / Live / IDE の共通画面・デスクトップ | `frontend_ide` | `npm test` |

| VS Code セットアップ・モデル候補・クリーンアップ | `frontend_ide/host` | `python -m unittest discover -s checks -p "test_*.py"` |
| Discord の Code / Live 中継・音声・設定・パネル | `frontend_channels/discord` | `npm run check` / `npm test` |
| Discord のセットアップ・起動・クリーンアップ連携 | プロジェクトルート | `python -X utf8 -m unittest discover -s frontend_channels/discord/checks -p "test_*.py"` |

外部AIを呼ばない単体テストでは、通信クライアントをモックにし、対象クラスのコンストラクターで状態を初期化する。子Pythonの標準出力・標準エラーをUTF-8として検証する場合は、子側でも `reconfigure(encoding='utf-8')` を指定する。親の `-X utf8` は子プロセスへ自動的には引き継がれない。

## 共有binが先に見つかる古い起動コマンドの更新

通常setup・単体setup・`--launchers-only` は、各コマンドの正規ランチャーを書いた後、既存の `~/.local/bin` の同一コピー生成ランチャーも毎回最新化する。対象は Diag / Memo / Avatar / IDE / Console / Browser / Navi / Code / Live / Task / Team / CPU / Discord / Slack。Hermes は元から共有binが正規配置で、従来通り毎回再登録する。IDE一括登録の `register_path=False` でも共有ランチャー更新を省略しない。

共通処理は `scripts/_setup_path.py:sync_shared_launcher`。所有印だけでなく生成テンプレート全体を照合し、Diag/Memo の旧 `backend_diag` と Avatar の旧 `_start.py` 入口も同じ配置元だけを移行する。Node/Python実行ファイルの更新は許容するが、追記コマンド・他コピー・リンクは更新せずエラーを返す。共有binがなければ新設しない。共有PATHや他アプリのランチャーを削除しない。

Windows で `where aidiy_diag` の最初が共有binでも、所有確認が通れば通常 `python _setup.py` の再実行で修復される。clone / pullだけでは生成済みコマンドは変わらない。登録失敗時は `_AIDIY\aidiy_diag\bin\aidiy_diag.cmd` を直接指定して起動元を固定し、エラーに示されたファイルの所有元を確認する。

検証: `python -m unittest scripts/checks/test_shared_launcher.py scripts/checks/test_shared_launcher_integration.py frontend_diag/checks/test_directory_migration.py scripts/checks/test_setup_path.py`。実ホーム・PATH・依存環境ではなく一時ホームと模擬登録を使う。
